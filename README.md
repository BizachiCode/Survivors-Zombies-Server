# Survivors vs Zombies – Card Tower Defense: authoritative server

Colyseus 0.18 + TypeScript server for the **Survivors vs Zombies – Card Tower Defense** Unity template. The server owns every rule; the Unity
client sends intents. The Unity project also ships an Offline backend with the same interface (`IBackendService`), so
the game can run without a server and switch later without changing gameplay code.

There is no login screen: every device owns a guest account created on its first launch. From the profile the player
can link an email + password, which lets the account be opened on another device or after a reinstall.

Battles are authoritative too: the server simulates every battle and the client plays a replica in deterministic
lockstep (the model of real-time competitive mobile games). The client only sends intents (place a card, pause, speed); the server
validates them, decides how the battle ends and grants the stars and rewards. See [Battles](#battles).

## Requirements

| Tool | Version |
| --- | --- |
| Node.js | 20.9 or newer |
| MySQL / MariaDB | MySQL 8+ or MariaDB 10.4+ |
| Redis | 6+ (active sessions). `SESSION_STORE=memory` runs without it on a single process. |

## Quick start (development)

Clone it **inside the Unity project folder** (next to `Assets`) as `CardTowerDefense-Server`: the Unity exporters write
`<project>/CardTowerDefense-Server/content`.

```bash
git clone https://github.com/BizachiCode/Survivors-Zombies-Server.git CardTowerDefense-Server
cd CardTowerDefense-Server
npm install
npm run devdb:init   # Windows + XAMPP only, once: private MariaDB on port 3307 (.devdb/), MYSQL_* written to .env
npm start            # creates or completes .env with random secrets, applies migrations, listens on ws://localhost:2567
```

Without a local Redis set `SESSION_STORE=memory` in `.env`. After a reboot run `npm run devdb:start` before `npm start`. With your own MySQL, skip `devdb:*` and set `MYSQL_*` in
`.env` instead (the user needs CREATE rights the first time; the database is created automatically).

Developer tools (`DEV_TOOLS=true`, never in production): `http://localhost:2567/monitor` and `/playground`.
`GET /health` answers the server state.

## Connecting the Unity client

`Assets/CardTowerDefenseTemplate/Res/Resources/BackendSettings.asset`: **Mode** `Online` and **Server Url**
`ws://127.0.0.1:2567` (use `wss://` in production). `Offline` runs everything on the device.

Game rules the server enforces (currencies, avatars, nickname rules, level curve) live in `src/config/game-config.ts`;
the Unity project mirrors them (`Res/Resources/AvatarCatalog`, the Offline backend), so change both together. Starting
balances of new accounts come from `START_COINS` / `START_GEMS` in `.env`.

## Battles

- **Simulation.** `src/modules/battle/sim` is a line-by-line port of the Unity core's `BattleSimulation` (C#). Both use
  IEEE doubles with the same operation order, so a battle gives the same result bit for bit on both sides;
  `test/battle_parity_test.ts` replays 24 battles generated by the C# code (`test/fixtures/battle-golden`) and checks every
  command result, a state hash every 20 ticks, every event and the final state. **Any change to the C# simulation needs
  the same change here**, then regenerate the fixtures:
  `cd Assets/CardTowerDefenseTemplate/Core/Tests~ && dotnet run -c Release -- --golden ../../../../CardTowerDefense-Server/test/fixtures/battle-golden`.
- **Content.** Cards, enemies, encounters, difficulties and campaign stages come from `content/battle-content.json`,
  written by Unity (*Tools > Card Tower Defense > Export Server Content*) from the project's `CampaignAsset`s. The server
  validates it at boot and sends each battle's numbers to the client, so balance changes need no client update: re-export
  and restart. Rewards per stage: victory, first clear bonus, defeat.
- **Rooms.** `campaign` (stage list with stars and unlocks) and `battle` (one room per battle). Protocol in
  `docs/PROTOCOL.md`.

## Card collection

Card progression, every rule from the content's `collection` (exported from the Unity `CollectionAsset`):

- **Unlocks.** Each card lists one or more ways to get it: `starter`, `seeds` (spend the card's seeds; wild seeds cover
  what is missing), `stage` (first win of a stage), `purchase` (coins or gems), `level` (player level). Seeds and
  purchases are player actions; the others are granted automatically (on `info` and after every battle result).
- **Levels.** Each card follows an upgrade curve: cost per level (any mix of currencies and items) and the health/damage
  multipliers of that level. Unity generates milestone (coins + XP, meteorites at 5/10/15/20), coins-only and seeds + coins
  curves; any value can be edited by hand.
- **Team.** Battles of `player` encounters use the player's team (up to `deckSize` cards) at their collection levels.
- **Abilities.** Each card can list its own abilities (e.g. level 5: +1 piercing hit): stat modifiers applied from their
  level on, validated at boot (every level must still be a valid card).
- **Items.** Seeds, upgrade XP and materials are stage rewards (victory, first clear, defeat) and shop goods, held in
  `user_items` and changed only by `InventoryLedger` (`item_ledger`). Room `collection`: `info`, `unlock`, `upgrade`, `set_deck`.

## Shop

Offers from the content's `shop` (exported from the Unity `ShopAsset`): a price in coins or gems, currencies and/or items
granted, an optional daily limit (reset at UTC midnight, `shop_purchases`) and an optional player level. Room `shop`:
`info`, `buy`.

## Missions, events and daily rewards

From the content's `progression` (exported from the Unity `ObjectivesAsset`): daily and weekly missions, achievement
chains (tiers claimed in order), time-limited events with their own goals, and a looping login calendar. Progress is
counted by the server inside the battle, collection, shop and daily transactions (never sent by the client); rewards
(currencies, items, experience) are credited through `RewardGranter`. Rooms `objectives` (`info`, `claim`, `claim_all`)
and `daily` (`info`, `claim`). The profile `info` answer adds the player's statistics.

## Battle modes and the arena

Every battle runs in the `battle` room; a mode decides what it is for (`src/modules/battle/battle-modes.ts`): `campaign`
(stages), `arena` and `tower` (event towers). A mode checks whether the player may play its target, says which encounter
runs, and settles the result inside the battle's transaction; new modes register with `BattleService.registerMode`.

**Arena** (content `arena`, Unity `ArenaAsset`): weekly seasons (Monday 00:00 UTC), leagues, groups of `groupSize`
players, tickets that regenerate (or are bought), matches scored by the server from the battle (kills, waves, victory,
base health). The season is settled the first time a player comes back: promotion / demotion by rank and the league's
reward by mail. Room `arena` (`info`, `buy_ticket`).

## Real-money purchases (IAP)

Gem packs and special offers (`shop.products`, exported from the Unity `ShopAsset`) are sold with Unity IAP 5 and
verified here before anything is granted: Google Play receipts by signature (`GOOGLE_PLAY_LICENSE_KEY`) and/or the
Google Play Developer API (`GOOGLE_PLAY_SERVICE_ACCOUNT_FILE`), App Store StoreKit 2 transactions by their JWS chain up to
the pinned Apple Root CA - G3 (`APPLE_BUNDLE_ID`), and Unity's Editor fake store only in development
(`IAP_ALLOW_FAKE_STORE`). Each store transaction grants once (`iap_purchases`, unique per store), receipts must belong to
the account that sends them, and the client confirms the store order only after the server answered. Room `iap`
(`info`, `verify`); setup in `Assets/CardTowerDefenseTemplate/Core/Documentation/Purchases.md`.

## Admin panel and refunds

`/admin` is a single-page panel (folder `admin/`, no build step) over the JSON API `/admin/api/*`: dashboard, player
search and detail, grant / remove currencies and items, mail, ban / unban, maintenance switch, news and mail broadcast
editors, manual refunds and an audit trail (`admin_audit`). It exists only when `ADMIN_TOKEN` (32+ characters) is set
(`ADMIN_ALLOWED_IPS` narrows it further). Refunded purchases are revoked automatically: App Store Server Notifications V2
at `POST /iap/apple/notifications` and a poller of Google's voided purchases API. Details, endpoints and the URLs to
configure in the stores: `docs/PROTOCOL.md`.

## Lucky wheel and friends

- **Wheel.** Segments, weights, free spins per day, the price of extra spins and a daily limit from the content's
  `wheel` (Unity `WheelAsset`); the server draws the segment (`crypto.randomInt`), charges and grants in one transaction.
  Room `wheel` (`info`, `spin`).
- **Friends.** Friend codes (the public id), requests (crossed requests become a friendship), limits, a daily gift per
  friend (collected with a daily cap) and public player cards with statistics. Room `friends`.

## News, mail, rankings and chat

- **News.** `content/news.json`: localized announcements (pinned, expiry, art key, link). Re-read when the file changes,
  no restart. Room `news`.
- **Mail.** `content/mail.json` broadcasts (delivered once per player, with attachments and a time window) plus mail
  sent by server code (`MailService.send`). Claim one or all, delete. Room `mail`.
- **Rankings.** Stars, level and wins boards (top 100 cached 60 s, the player's own rank always computed). Room `ranking`.
- **Chat.** Global channel with history, sanitizing, word filter, rate limit and auto-mute for repeated messages (state
  in process memory). Room `chat`.

Unity writes both files with *Tools > Card Tower Defense > Export Live Content* (from the `NewsAsset` and `MailAsset`
of the project: one of each, found anywhere under `Assets`).

## Scripts

| Script | What it does |
| --- | --- |
| `npm start` | development server with reload |
| `npm run build`, `npm run start:prod` | compile to `build/`, run the compiled server |
| `npm run typecheck` | type-check `src/` and `test/` |
| `npm test` | unit and room-protocol tests (no database or Redis needed) |
| `npm run test:e2e` | the real server against MySQL + Redis, database `ctd_e2e` |
| `npm run db:generate`, `db:migrate`, `db:studio` | Drizzle schema tools |
| `npm run devdb:init`, `devdb:start`, `devdb:stop` | local MariaDB instance (Windows, XAMPP binaries) |

## Production

```bash
npm run build
NODE_ENV=production npm run start:prod
```

Production refuses to boot with missing, default or short secrets: set `JWT_ACCESS_SECRET`, `PASSWORD_PEPPER`,
`REFRESH_PEPPER`, `DEVICE_PEPPER` (long random strings, e.g. `openssl rand -base64 48`), `MYSQL_*` and `REDIS_*`.
Behind a reverse proxy set `TRUST_PROXY` / `TRUSTED_PROXIES`; WebGL builds need `CORS_ORIGINS`.

## Layout

```
src/
  app.config.ts      Colyseus rooms, HTTP and boot hooks
  app/               composition root (container.ts) and HTTP routes
  config/            validated environment (env.ts) and enforced game rules (game-config.ts)
  infrastructure/    Drizzle (MySQL), migrations, Redis session store
  modules/<feature>/ *.room.ts (transport, zod) -> *.service.ts (rules) -> *.repository.ts (Drizzle only)
                     auth, account, profile; economy (WalletLedger: the only writer of balances);
                     battle (sim/ simulation port, content/ catalog, campaign + battle rooms, rewards);
                     collection (cards, levels, abilities, team; InventoryLedger: the only writer of items);
                     shop (offers, daily limits); objectives (missions, achievements, events, daily);
                     news, mail, ranking, chat; iap (receipt validators, refunds); wheel; friends; admin (panel API, audit)
  shared/            errors, room base classes, request handler, security helpers
admin/               static admin panel (index.html, app.js, style.css)
content/             content exported from Unity (battle-content.json, news.json, mail.json)
drizzle/             SQL migrations, applied in order on start (DB_AUTO_MIGRATE) or with `npm run db:migrate`
docs/PROTOCOL.md     every room, request and answer
test/                unit + protocol tests (in-memory repositories), e2e
tools/devdb.ps1      local development database
```
